## 🎯 Core Understanding

**ACES** is not just an agent framework—it's a *spec-driven AI engineering platform* with three distinct value layers:

```
Engineer writes WHAT they want (Spec)
        ↓
ACES figures out HOW to build/run it (Execution + Generation)
        ↓
ARIA governs WHETHER it should run (Trust + Risk + Audit)
```

The brilliance here is sequencing: you've resolved the "three conversations" by mapping them to phased delivery rather than treating them as conflicting requirements.

---

## 🔑 Key Architectural Insights

### 1. **Governance as a First-Class Layer**
ARIA isn't bolted on—it's the central nervous system. The four-outcome decision engine (Allow/Warn/Block/Explain) with "Decision Archaeology" is enterprise-ready thinking. This directly addresses JPMorgan's compliance reality.

### 2. **Oracle 23ai-Centric Data Strategy**
Your "Oracle first, add only when justified" principle is disciplined:
- ✅ Vector Search → Oracle AI Vector (no Qdrant)
- ✅ Full-text → Oracle Text (no Elasticsearch)
- ✅ Async → Oracle AQ (no Kafka in P1/P2)
- ✅ Isolation → Oracle VPD (row-level security at DB engine)

This reduces operational complexity while meeting SOX/regulatory requirements natively.

### 3. **Spec-Driven Flow Positioned Correctly**
The 7-step flow (YAML → IR → DAG → ARIA Validate → Generate → Deploy → Learn) is powerful—but critically, it's marked as **Phase 2**. This prevents scope creep during Innovation Week while preserving the long-term vision.

### 4. **Dual-Audience Experience Layer**
| Audience | Interface | Primary Need |
|----------|-----------|-------------|
| Engineers | Spec Builder UI + CLI + API | "Build and iterate fast" |
| Management | Executive Dashboard | "What does this cost/risk?" |

🔐 What is OpenAI Privacy Filter?
OpenAI Privacy Filter is a newly released AI model designed to detect and remove sensitive personal data (PII) from text automatically. 

Think of it as a privacy shield that sits between your data and AI systems.

👉 Example
Input:

“Call me at +91-9876543210 or email xyz@gmail.com”

Output:

“Call me at [PRIVATE_PHONE] or email [PRIVATE_EMAIL]” 

🧠 What makes it different?

It doesn’t just look for patterns like “@gmail.com”.
It understands context, so it knows when something is actually private vs public. 

2. Works locally (huge deal)
It can run on your machine, meaning:

Your raw data never leaves your system

No accidental leaks to APIs

This is critical for enterprise and banking use cases. 

3. High-speed, single-pass processing
It scans large text quickly and redacts everything in one pass, making it suitable for:

Logs

Documents

Training datasets 

4. Covers multiple sensitive data types
It can detect things like:

Names

Emails

Phone numbers

Addresses

Account numbers

Passwords / API keys 

5. Open-weight (developer friendly)
Available openly (Apache 2.0 license)

Can be customized and integrated into apps

Works in pipelines like:

Data preprocessing

AI training

Content moderation

## 🎯 What Is ARIA?

**ARIA** = **Autonomous Risk & Intelligence Advisor** (or similar—name may evolve)

### In One Sentence:

---

## 🔍 ARIA vs ACES: The Distinction

| Dimension | **ARIA** (Upstream) | **ACES** (Core) |
|-----------|---------------------|-----------------|
| **Primary Role** | Strategy, policy, risk intelligence | Execution, orchestration, verification |
| **Input** | Business rules, compliance policies, risk models, historical data | Signals, events, state changes from systems |
| **Output** | Decisions, policies, trust scores, explainability | Actions, workflows, verified outcomes |
| **Question It Answers** | *"Should we act? What's the safest way? What's the risk?"* | *"How do we execute this action and confirm it worked?"* |
| **AI Usage** | Heavy: reasoning, optimization, explainability, pattern detection | Light/Optional: AI-assisted strategy selection, but execution is deterministic |
| **Governance** | Defines policies, approval workflows, risk thresholds | Enforces policies, logs decisions, ensures auditability |

### Mental Model:
```
ARIA = Strategy + Governance + Trust Intelligence
ACES = Execution + Orchestration + Verification

ARIA decides WHAT and WHY
ACES handles HOW and CONFIRMS
```

---

## 🔗 When & Why Combine ARIA with ACES

### ✅ Combine When:
1. **You need intelligent decision-making** beyond simple rules
   - ARIA evaluates complex risk scenarios; ACES executes the chosen action

2. **Enterprise compliance is non-negotiable**
   - ARIA encodes SOX, GDPR, internal policies; ACES enforces them at execution time

3. **You want explainable automation**
   - ARIA generates human-readable reasoning; ACES logs the full audit trail

4. **Risk-aware execution is required**
   - ARIA assigns trust scores and risk levels; ACES adjusts execution strategy accordingly

5. **You're scaling across teams/seals**
   - ARIA manages cross-team policies; ACES respects seal-level ownership boundaries

### ❌ Don't Combine (Yet) When:
1. **You're building MVP/Phase 1**
   - Start with ACES rule-based decisions; add ARIA in Phase 2 for intelligence

2. **Use cases are simple and deterministic**
   - If "if drift → restart" works, you don't need ARIA's complexity yet

3. **Team capacity is limited**
   - Build ACES foundation first; ARIA is a force multiplier, not a prerequisite

### **4.2 DATABASE SCHEMA**

```sql
-- Workflow State Table
CREATE TABLE workflow_state (
    workflow_id VARCHAR(100) PRIMARY KEY,
    correlation_id VARCHAR(100) NOT NULL,
    status VARCHAR(50) NOT NULL, -- PENDING, IN_PROGRESS, COMPLETED, FAILED
    current_step VARCHAR(100),
    skill_name VARCHAR(100),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- Audit Log Table
CREATE TABLE audit_log (
    id SERIAL PRIMARY KEY,
    correlation_id VARCHAR(100) NOT NULL,
    workflow_id VARCHAR(100),
    event_type VARCHAR(50) NOT NULL, -- SIGNAL, DECISION, ACTION, VERIFICATION
    event_data JSONB,
    timestamp TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- Decision Log Table
CREATE TABLE decision_log (
    id SERIAL PRIMARY KEY,
    correlation_id VARCHAR(100) NOT NULL,
    rule_applied VARCHAR(100),
    strategy_selected VARCHAR(100),
    confidence_score DECIMAL(3,2),
    reasoning TEXT,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- Policy Store Table
CREATE TABLE policies (
    policy_id VARCHAR(100) PRIMARY KEY,
    name VARCHAR(200) NOT NULL,
```

### **Core Interfaces (4 Key Contracts):**

#### **1. Orchestrator Interface**
```java
public interface Orchestrator {
    Object execute(WorkflowDefinition workflow, Map<String, Object> input);
}
```
**Purpose**: Defines how workflows are executed

#### **2. ToolGateway Interface**
```java
public interface ToolGateway {
    ToolResult execute(ToolRequest request);
}
```
**Purpose**: Abstraction for external tool interaction

#### **3. AgentService Interface**
```java
public interface AgentService {
    AgentResult process(String input);
}
```
**Purpose**: Interface for agent interactions

#### **4. RunLedger Interface**
```java
public interface RunLedger {
    void log(RunEvent event);
}
```
**Purpose**: Logging events during execution

### **Domain Models:**

**WorkflowDefinition**: Complete workflow with name and steps
**WorkflowStep**: Single step (TOOL or AGENT type)
**RunEvent**: Execution event (step name, status, output, cost, timestamp)
**ToolRequest**: Tool invocation details
**ToolResult**: Tool execution outcome
**AgentResult**: Agent processing result

### **Implementations:**

#### **SimpleOrchestrator (Core Engine)**
**Responsibilities:**
1. Accept WorkflowDefinition + input
2. Execute steps sequentially
3. Delegate to ToolGateway for TOOL steps
4. Delegate to AgentService for AGENT steps
5. Log each step via RunLedger
6. Return final output

#### **Mock Implementations (For Demo)**
- **MockToolGateway**: Simulates tool execution (get-ci-logs, get-git-diff)
- **MockAgentService**: Returns generic summary/plan

## 1. WELCOME & OVERVIEW

### **Purpose**
Welcome to **ACES (Autonomous Cognitive Engineering System)** - a governed agentic execution platform that transforms real-time signals into automated, verified outcomes.

### **Quick Facts**
- **Goal**: Automate the full lifecycle from detection → decision → execution → verification
- **Core Philosophy**: Observed State == Desired State (with governance)
- **MVP Focus**: Runtime Certificate Enforcement (CertGuardian integration)
- **Team Size**: 2-7 members
- **Timeline**: 4 weeks to MVP

### **Key Concepts**
| Term | Definition |
|------|------------|
| **Signal** | Event indicating system state (e.g., cert mismatch) |
| **Drift** | Mismatch between observed and desired state |
| **Skill** | Declarative, reusable automation unit |
| **Seal** | Team/ownership boundary |
| **Closed-Loop** | Signal → Decision → Execution → Verification |

## 2. WHAT IS ACES?

### **Problem We Solve**
```
Current State:
  System detects issue ✓
  Human investigates ✗
  Human fixes manually ✗
  Verification inconsistent ✗

ACES Solution:
  System detects issue ✓
  ACES decides automatically ✓
  Executes via existing systems ✓
  Verifies outcome ✓
```

### **Core Capabilities**
1. **Signal Ingestion** - Accept events from CertGuardian, monitoring, etc.
2. **State Evaluation** - Detect drift/mismatch
3. **Decision Engine** - Determine action needed
4. **Workflow Orchestration** - Execute skills
5. **Governance** - Policy enforcement
6. **Verification** - Confirm outcome
7. **Observability** - Full audit trail

### **What ACES Is NOT**
- ❌ Monitoring tool (consumes signals, doesn't generate)
- ❌ CI/CD system (triggers pipelines, doesn't replace)
- ❌ Direct execution system (uses agents/pipelines)

```
## 1. WELCOME & PROJECT OVERVIEW

### **Project Vision**
**ACES (Autonomous Cognitive Engineering System)** is a governed agentic execution platform that transforms real-time signals into automated, verified outcomes.

### **Problem We Solve**
```
Current State:
  System detects issue ✓
  Human investigates ✗
  Human fixes manually ✗
  Verification inconsistent ✗

ACES Solution:
  System detects issue ✓
  ACES decides automatically ✓
  Executes via existing systems ✓
  Verifies outcome ✓
```

### **Core Capabilities**
1. **Signal Ingestion** - Accept events from CertGuardian, monitoring, etc.
2. **State Evaluation** - Detect drift/mismatch
3. **Decision Engine** - Determine action needed
4. **Workflow Orchestration** - Execute skills
5. **Governance** - Policy enforcement
6. **Verification** - Confirm outcome
7. **Observability** - Full audit trail

### **Key Use Cases**
1. **Runtime Certificate Enforcement** (CertGuardian) - MVP
2. **Incident Auto-Remediation** - Phase 2
3. **Crypto Compliance & PQC Readiness** - Phase 3

---

## 2. WHAT IS ACES?

### **Simple Explanation**
ACES is the intelligent layer that sits between *"something is wrong"* and *"it's been fixed"* — ensuring every action is **decided, governed, executed, and verified** automatically.

### **The ACES Loop**
```
Signal → Evaluate → Decide → Govern → Execute → Verify → Observe
```

### **What ACES Is**
✅ A decision and orchestration layer  
✅ A governed execution platform  
✅ A closed-loop verification system  
✅ A reusable skill-based automation engine  

### **What ACES Is NOT**
❌ Monitoring tool (consumes signals, doesn't generate)  
❌ CI/CD system (triggers pipelines, doesn't replace)  
❌ Direct execution system (uses agents/pipelines)
```

### 🗄️ Oracle 23ai Schema (MVP)
```sql
-- Workflow State
CREATE TABLE workflow_state (
    workflow_id VARCHAR2(100) PRIMARY KEY,
    correlation_id VARCHAR2(100) NOT NULL,
    status VARCHAR2(50),
    current_step VARCHAR2(100),
    skill_name VARCHAR2(100),
    created_at TIMESTAMP DEFAULT SYSTIMESTAMP,
    updated_at TIMESTAMP DEFAULT SYSTIMESTAMP
);

-- Decision Log
CREATE TABLE decision_log (
    id NUMBER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    correlation_id VARCHAR2(100) NOT NULL,
    rule_applied VARCHAR2(100),
    strategy_selected VARCHAR2(100),
    confidence_score NUMBER(3,2),
    reasoning CLOB,
    created_at TIMESTAMP DEFAULT SYSTIMESTAMP
);

-- Audit Trail
CREATE TABLE audit_log (
    id NUMBER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    correlation_id VARCHAR2(100),
    workflow_id VARCHAR2(100),
    event_type VARCHAR2(50),
    event_payload CLOB,
    timestamp TIMESTAMP DEFAULT SYSTIMESTAMP
);

-- Policy Store
CREATE TABLE policies (
    policy_id VARCHAR2(100) PRIMARY KEY,
    name VARCHAR2(200),
    rules JSON,
    environment VARCHAR2(50),
    created_at TIMESTAMP DEFAULT SYSTIMESTAMP
);

-- Skill Registry
CREATE TABLE skills (
    skill_id VARCHAR2(100) PRIMARY KEY,
    name VARCHAR2(200),
    version VARCHAR2(20),
    definition JSON,
    created_at TIMESTAMP DEFAULT SYSTIMESTAMP
);
```

```java
package com.jpmc.aces.ingestion.controller;

import com.jpmc.aces.common.model.Signal;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;
import org.springframework.web.client.RestTemplate;
import org.springframework.http.ResponseEntity;

import java.util.UUID;

@RestController
@RequestMapping("/api/v1/signals")
public class SignalController {

    private final RestTemplate restTemplate;
    // URL of Evaluation Service (In MVP, assume running locally or via service discovery)
    private final String evaluationServiceUrl = "http://localhost:8081/api/v1/evaluate";

    public SignalController(RestTemplate restTemplate) {
        this.restTemplate = restTemplate;
    }

    @PostMapping
    public ResponseEntity<?> ingestSignal(@RequestBody Signal signal) {
        // 1. Validate Signal
        if (signal.getType() == null || signal.getPayload() == null) {
            return ResponseEntity.badRequest().body("Invalid Signal Format");
        }

        // 2. Generate Correlation ID
        String correlationId = UUID.randomUUID().toString();
        signal.setTimestamp(java.time.Instant.now());

        // TODO: In Phase 1, log to audit service.
        System.out.println("[INGESTION] Received signal: " + signal.getType() + " | ID: " + correlationId);

        // 3. Forward to Evaluation Service
        try {
            // Passing the signal payload and correlationId to Evaluation
            // Note: Create a wrapper DTO if needed, or pass signal directly
            restTemplate.postForObject(evaluationServiceUrl + "?correlationId=" + correlationId, 
                                       signal, String.class);
        } catch (Exception e) {
            // Fallback or Dead Letter Queue logic would go here
            System.err.println("[INGESTION] Failed to forward to evaluation: " + e.getMessage());
        }

        return ResponseEntity.ok().body(new ApiResponse("accepted", correlationId));
    }

    private record ApiResponse(String status, String correlationId) {}
}
```

### **`EvaluationService.java`**

```java
package com.jpmc.aces.evaluation.service;

import com.jpmc.aces.common.model.Signal;
import org.springframework.web.bind.annotation.*;
import org.springframework.web.client.RestTemplate;

@RestController
@RequestMapping("/api/v1/evaluate")
public class EvaluationController {

    private final RestTemplate restTemplate;
    private final String decisionServiceUrl = "http://localhost:8082/api/v1/decide";

    public EvaluationController(RestTemplate restTemplate) {
        this.restTemplate = restTemplate;
    }

    @PostMapping
    public void evaluateSignal(@RequestParam String correlationId, @RequestBody Signal signal) {
        System.out.println("[EVALUATION] Analyzing drift for " + signal.getApplication());

        // MVP Logic: CertGuardian Drift Detection
        String expected = signal.getPayload().get("expected_thumbprint");
        String observed = signal.getPayload().get("observed_thumbprint");

        boolean driftDetected = !expected.equals(observed);

        // TODO: Store Evaluation Result in DB

        // Forward to Decision Engine if drift is detected
        if (driftDetected) {
            EvaluationPayload payload = new EvaluationPayload(
                correlationId, signal, "CERT_DRIFT", true
            );
            
            try {
                restTemplate.postForObject(decisionServiceUrl, payload, String.class);
            } catch (Exception e) {
                System.err.println("[EVALUATION] Decision Engine unreachable: " + e.getMessage());
            }
        } else {
            System.out.println("[EVALUATION] No drift detected. Signal ignored.");
        }
    }

    private record EvaluationPayload(String correlationId, Signal signal, String issueType, boolean actionRequired) {}
}
```
