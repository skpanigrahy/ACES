ACES SDD — CI/CD Auto-Fix
SDD FRAMEWORK — CI/CD AUTO-FIX USE CASE
Input → Process → Output
SDD is a compiler. You give it a specification. It produces working code. Here is exactly what you need to provide, what SDD does with it, and what comes out the other end.
THE MENTAL MODEL
Think of SDD like a senior engineer who has never worked at JPMC before.

You must tell them: What problem to solve · What the system looks like · What tools exist · What rules to follow · What success looks like.

You do NOT need to tell them: How to write a Spring Boot service · How to use Resilience4j · How to structure tests. They already know that — that is the SDD framework's job.

PROCESS
What SDD Does
1. Parse + Validate
Reads all spec YAML. Validates against JSON Schema. Rejects malformed specs before generating anything.
2. Build IR
Converts YAML → Intermediate Representation. Strictly typed. No ambiguity. Same spec = same IR always.
3. DAG Planning
Breaks IR into task graph. What to generate first. What depends on what. Parallel tasks identified.
4. ARIA Validation
ARIA scores the spec for risk before generating any code. High-risk specs blocked.
5. Code Generation
Freemarker templates + LLM. Generates Java classes, tests, configs, Flyway migrations.
6. Validate + Fix
Compiles generated code. Runs tests. Feeds failures back to LLM. Auto-fix loop (max 3 iterations).

INPUT — WHAT YOU GIVE SDD
The 6 Specification Files You Must Write
These are the inputs SDD needs to generate the CI/CD auto-fix module. Each is a YAML file. Together they form the complete spec that SDD compiles into working code.
THE GOLDEN RULE FOR INPUTS
Be specific about WHAT and WHY. Never tell SDD HOW. The moment you start saying "use a HashMap here" or "write a for loop" you are fighting the framework. Tell SDD what behaviour you need. It decides the implementation. Your job is domain knowledge. SDD's job is code.
1
Business Specification
What problem are we solving · Who benefits · What does success look like
This tells SDD the business context. Without this, generated code solves a technical problem but may not solve the actual business problem. SDD uses this to name things correctly, write meaningful comments, and generate accurate error messages.
goal — mandatory users — mandatory constraints — mandatory success_metrics — recommended non_goals — recommended

WHAT YOUR TEAM MUST FIND OUT ABOUT JULES
Before running SDD, your DevOps engineer must answer these four questions by checking the Jules documentation or asking the Jules team:

1. What is the exact webhook payload format Jules sends on a stage failure?
2. What authentication does Jules use for outbound webhooks? (HMAC? Bearer? Custom header?)
3. What is the Jules API endpoint to retrigger a pipeline? (POST /api/pipelines/{id}/retrigger?)
4. How does Jules report which scanner failed and what the results are — inline in the webhook or via a separate results URL?
